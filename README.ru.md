## Зачем я это сделал

Я начал делать этот проект, когда полез в старые Windows x86 бинарники, которые вообще не создавались с расчётом на комфортную реконструкцию.

И я постоянно упирался в одну и ту же проблему:

- таблицы экспортов **недостаточно**
- вывода декомпилятора **недостаточно**
- писать совместимую proxy DLL **вручную** — долго и муторно
- а пытаться сразу восстановить весь исходник — почти всегда плохая стратегия

Поэтому вместо того, чтобы каждый раз заново собирать один и тот же glue-код, я сделал пайплайн, который сначала даёт мне **рабочий proxy DLL-каркас**, а уже потом я спокойно уточняю ABI, calling convention, сигнатуры и внутреннюю логику.

Именно эту задачу я и хотел решить.

---

## Что делает этот проект

ReverseProxyDLL помогает быстро построить **собираемый совместимый каркас** для существующей legacy x86 Windows DLL.

Он позволяет генерировать proxy-проект, который:

- загружает оригинальную DLL во время выполнения
- резолвит экспорты через `GetProcAddress`
- проксирует совместимые вызовы
- сохраняет ordinals и структуру экспортов под контролем
- поддерживает логирование и runtime-трассировку
- даёт аккуратную основу для дальнейшего реверса и реконструкции

Это позволяет мне не тратить время на бесконечный шаблонный код и сосредоточиться на настоящем `reverse engineering`.

---

## Чем это отличается от обычных DLL proxy generators

Большинство генераторов proxy DLL умеют только следующее:

- прочитать export table
- сгенерировать обёртки
- пробросить вызовы

Это полезно, но для реального реверса старых бинарников этого мало.

Этот проект построен вокруг более практичного подхода:

- **учёт экспортов**
- **учёт ABI**
- **ориентация на reverse engineering**
- **ручные overrides там, где автоматике доверять нельзя**

Он понимает, что экспорты бывают разными.

Например, он может различать:

- обычные C exports
- C++ scoped / mangled exports
- data exports
- CRT / runtime forward exports

И в старых x86 DLL это критически важно.

---

## Текущий рабочий процесс

Обычно процесс выглядит так:

1. Снять дамп экспортов с оригинальной DLL
2. Посмотреть функции в Ghidra
3. Сгенерировать overrides / сигнатуры
4. Сгенерировать proxy-каркас
5. Собрать подменную DLL
6. Запустить целевое приложение
7. Дорабатывать ABI и логику по мере необходимости

То есть теперь я не начинаю каждый раз с нуля.

Я начинаю уже с **рабочего 80–90% каркаса** и дальше просто довожу его до ума.

## Toolchain / область применения

Этот проект изначально сделан с прицелом на **legacy-first сценарии**.

Он изначально строился вокруг:

- **Windows x86**
- **старых native DLL**
- совместимости со стилем **Visual C++ 2003 / VC7.1**
- reverse engineering задач, где бинарная совместимость важнее, чем современный комфорт сборки

Генерируемый каркас специально делается максимально простым и низкоуровневым, чтобы его при необходимости можно было адаптировать и под более современные версии MSVC.

Но если говорить честно:

> проект в первую очередь нацелен на **legacy x86 Windows DLL reconstruction и proxy compatibility work**.

Если он хорошо встанет и на более новые цели — отлично.  
Но основная цель у него именно старая Windows-совместимость.

## Основные инструменты

### [`generate_overrides_from_ghidra_dump.py`](src/generate_overrides_from_ghidra_dump.py)

Анализирует выходные данные декомпилятора в стиле Ghidra и генерирует структурированные метаданные `overrides.json`.

Полезно для:

- извлечения сигнатур
- нормализации псевдотипов
- определения соглашений о вызове функций
- генерации определений функций, готовых к переопределению

### [`reverse_dll_project_generator.py`](src/reverse_dll_project_generator.py)

Генерирует структуру прокси-DLL с поддержкой обратного преобразования на основе метаданных экспорта и необязательных переопределений.

Полезно для:

- генерации прокси-DLL
- создания структуры обертки экспорта
- управления компоновкой DEF/экспорта
- рабочих процессов замены устаревших DLL

---

## Пример рабочего процесса

Типичный запуск выглядит следующим образом:

```bash
python src/generate_overrides_from_ghidra_dump.py functions_dump.c overrides.generated.json
python src/reverse_dll_project_generator.py exports.md -o generated_proxy --dll-name dacom --original-dll dacom_addon.dll --overrides overrides.generated.json
```

Полные шаги настройки и сборки см. в [Startup](docs/STARTUP.md).

## Чем этот проект **не является**

Этот инструмент **не** “магически восстанавливает весь исходный код DLL”.

Он **не** гарантирует, что каждая сигнатура автоматически будет идеальной.

Он **не** заменяет сам reverse engineering.

Но он делает более практичную вещь:

> даёт быстрый, структурированный и собираемый старт для бинарно-совместимой реконструкции.

---

## Подходит для

- реверса старых Windows x86 DLL
- создания совместимых proxy-обёрток
- реконструкции старых игровых / системных модулей
- исследования ABI
- экспериментов с DLL replacement
- runtime-трассировки и постепенного ухода от оригинального бинаря

---

## Статус

Проект развивается на основе реальной практики восстановления legacy DLL.

Главная цель простая:

> сократить путь от “у меня есть бинарник” до “у меня есть рабочий proxy-compatible каркас”.
