# Proxy DLL Generation

This project allows you to generate a **proxy DLL project** for an existing Windows library using:

- a **function dump** exported from Ghidra
- a **real export list** extracted from x32dbg

The result is a generated **C/C++ proxy DLL project** that can be compiled and used as a wrapper around the original library.

---

## Requirements

Before starting, make sure you have:

- [Python 3](https://www.python.org/)
- [Ghidra](https://github.com/nationalsecurityagency/ghidra)
- [x32dbg](https://github.com/x64dbg/x64dbg)
- **Microsoft Visual C++ Toolkit 2003** _(recommended for old legacy DLLs)_
- **Microsoft Platform SDK for Windows Server 2003 R2**

> [!NOTE]
> If you are working with an old game or legacy x86 binary, using the original-era toolchain may be important for ABI compatibility.

---

## General Pipeline

```text
Ghidra -> functions_dump.c -> overrides.json
x32dbg -> exports.md
exports.md + overrides.json -> generated_proxy/
generated_proxy/ -> build -> proxy DLL
```

---

## 1. Export function dump from Ghidra

First, export the recognized functions from your target DLL using **Ghidra**.

### Steps

1. Open your DLL in **Ghidra**
2. Export the program:
   - `File`
   - `-> Export Program`
   - `-> Format -> C/C++`
   - `-> Output File -> functions_dump.c`

### Why this file is needed

This dump is used to extract:

- function return types
- calling conventions
- parameter types
- internal function signatures

> [!IMPORTANT]
> `functions_dump.c` is **not** the real export table of the DLL.
> It is only a decompiled function dump generated by Ghidra.

### Example

```c
undefined1 * __fastcall FUN_065b13e0(undefined1 *param_1)

{
  int iVar1;
  undefined1 local_1;

  local_1 = (undefined1)((uint)param_1 >> 0x18);
  *param_1 = local_1;
  iVar1 = FUN_065b5ece();
  *(int *)iVar1 = iVar1;
  *(int *)(iVar1 + 4) = iVar1;
  *(int *)(param_1 + 4) = iVar1;
  *(undefined4 *)(param_1 + 8) = 0;
  FUN_065b1480(param_1,0);
  return param_1;
}
```

---

## 2. Generate `overrides.json`

Once you have `functions_dump.c`, generate the function signature map.

### Command

```sh
python generate_overrides_from_ghidra_dump.py functions_dump.c overrides.json
```

### Arguments

- `functions_dump.c` — the Ghidra function dump
- `overrides.json` — output JSON file with parsed function metadata

### Why this file is needed

`overrides.json` helps the generator understand:

- return types
- calling conventions (`__cdecl`, `__stdcall`, `__fastcall`)
- parameters
- special cases like data exports or problematic symbols

> [!WARNING]
> Ghidra may export **invalid or noisy symbols**, for example:
>
> - `OptionalHeader.AddressOfEntryPoint`
> - CRT symbols such as `stricmp`
> - internal helper labels
> - data exports
>
> These may require manual cleanup in `overrides.json`.

### Example [overrides.json](examples/overrides.json)

```json
{
	"FDUMP": { "kind": "data_export" },
	"stricmp": {
		"kind": "c_export",
		"return_type": "int",
		"calling_convention": "__cdecl",
		"params": [
			{ "type": "const char*", "name": "str1" },
			{ "type": "const char*", "name": "str2" }
		]
	}
}
```

---

## 3. Extract real DLL exports into `exports.md`

Now you need the **actual export list** from the DLL.

### Steps using x32dbg

1. Open the target DLL in **x32dbg** _(x86 if the DLL is 32-bit)_
2. Open the:
   - `Symbols` tab

3. Select your loaded DLL
4. Copy the list of exported symbols
   - On the right there will be a list of exported functions
     - ![alt text](../media/exports.png)
5. Save them into a file called:

```text
exports.md
```

6. Example content - [exports.md](examples/exports.md)

> [!IMPORTANT]
> `exports.md` is the **real source of truth** for what the DLL actually exports.

> [!NOTE]
> Ghidra decompilation and PE exports are **not the same thing**.
> Always use the export table from x32dbg / PE metadata for final proxy generation.

---

## 4. Generate the proxy DLL project

Once you have:

- `exports.md`
- `overrides.json`

you can generate the proxy project.

### Command

```sh
python reverse_dll_project_generator.py exports.md -o generated_proxy --dll-name dacom --original-dll dacom_addon.dll --overrides overrides.json
```

### Arguments

- `exports.md` — export list from x32dbg
- `-o generated_proxy` — output folder for the generated project
- `--dll-name dacom` — name of the original DLL being cloned
- `--original-dll dacom_addon.dll` — filename that will be used for the renamed original DLL
- `--overrides overrides.json` — parsed function metadata from Ghidra

### Result

A new folder will be created:

```text
generated_proxy/
```

Inside it you will get:

- generated C/C++ proxy source files
- `.def` file
- loader code
- headers
- `build.bat`

---

## 5. Build the generated project

If the target DLL is old, you may need to compile it with an older toolchain to preserve compatibility.

Recommended for old binaries:

- **Microsoft Visual C++ Toolkit 2003**
- **Microsoft Platform SDK for Windows Server 2003 R2**

---

## 6. Prepare VC71 build environment

Create a file next to `build.bat` called:

```text
vc71_env.bat
```

### Example content [vc71_env.bat](examples/vc71_env.bat)

```bat
@echo off
set VC71=C:\Program Files (x86)\Microsoft Visual C++ Toolkit 2003
set SDK=C:\Program Files\Microsoft Platform SDK for Windows Server 2003 R2\

set PATH=%VC71%\bin;%SDK%\Bin;%PATH%
set INCLUDE=%VC71%\include;%SDK%\Include
set LIB=%VC71%\lib;%SDK%\Lib

echo =====================================
echo VC71 + Platform SDK environment ready
echo =====================================
cmd
```

### Update these paths

Replace with your own local paths:

- `VC71=<your path>`
- `SDK=<your path>`

### Useful downloads

- [Microsoft Visual C++ Toolkit 2003](https://archive.org/details/microsoft-visual-c-toolkit-2003)
- [Microsoft Platform SDK for Windows Server 2003 R2](https://archive.org/details/platform-sdk-for-microsoft-windows-server-2003-r2-march-2006-edition-english)

---

## 7. Build the DLL

1. Run:

```bat
vc71_env.bat
```

2. Then run:

```bat
build.bat
```

If everything is correct, the compiled DLL will appear in:

```text
build/
```

---

## 8. Replace the original DLL

Now prepare the final deployment.

### Example

Suppose the original DLL was:

```text
dacom.dll
```

### Steps

1. Rename the original DLL to:

```text
dacom_addon.dll
```

2. Place both files side by side:

```text
dacom.dll          <- newly generated proxy DLL
dacom_addon.dll    <- original renamed DLL
```

> [!IMPORTANT]
> `dacom_addon.dll` is just an example name.
> You can use any filename you want, but it **must match** the value passed to:

```sh
--original-dll dacom_addon.dll
```

## Important Notes

### 1. Not all exports are simple

Some exports may be:

- `__stdcall`
- `__cdecl`
- C++ mangled names
- overloaded functions
- data exports
- CRT / runtime symbols

Because of that, you may need to manually adjust:

- `overrides.json`
- generated signatures
- `.def` file
- proxy wrappers

---

### 2. Ghidra signatures are not always correct

Always verify if needed:

- calling convention
- return type
- parameter count
- mangled name meaning

Useful tools:

- Ghidra
- x32dbg
- PE-bear
- dumpbin
- Dependency Walker

---

### 3. First-generation output often needs manual cleanup

This project is designed to **accelerate proxy DLL reconstruction**, not to guarantee a perfect 100% automatic rebuild.

It is most useful as a base for:

- reverse engineering
- runtime wrapping
- export reconstruction
- ABI-compatible proxy layers
